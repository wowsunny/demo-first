# 在 Claude Code 里试用

## 验证到哪一步

2026-11-19，在 Claude Code 桌面应用的一个会话里实跑了三轮。

做法：新开一个没有上下文的 agent 当调度者（模型 Sonnet 5.5），只把技能目录告诉它，让它照 `SKILL.md` 和 `references/claude-code-platform.md` 做一个小项目：网页版番茄钟，两小时的冲刺，一个没把握的点（结束时的提示音用哪一种）。开子代理用的是真实的 Agent 工具，传话用的是真实的 SendMessage。用户不在场，用户的回复照事先写好的剧本给。

三轮用的都是**后台子代理**这一种开法。

另一种开法（子会话）是之后加的，2026-11-20 试了一次：主会话照适配文件开出探索者和总建设者两个真的子会话，监管者用子代理。结果：

- 会话只凭几行平台说明和派工单的路径就能开工；回报写进了 `coord/tasks/<编号>.md`；每轮结束的通知到了主会话；主会话发的消息，会话做完手头的事就读到并照做了；用户直接进探索者的会话选定了提示音。
- 但它重得多。同样的角色、同一个模型，子会话用了 33 到 35 分钟、约 25 万输出 token；子代理是 5 到 7 分钟、1 到 1.6 万。记录里看得到的原因有两处：子会话没设思考强度时继承主会话的（那次是最高档），子代理用的是中档；子会话带着完整会话的全套规矩，会自己补测试、做验证。这两处各占多少没有分开测。

所以子会话这种开法的规则还要改，现在适配文件里只先加了一条：开会话时把思考强度明确设成 high。

| 轮次 | 做到哪 | 结果 |
|---|---|---|
| 第一轮 | 立项、派工、探索者两轮传话、定稿、落地、阶段报告、监管者巡检 | 走通，约 7 分钟。开了总建设者、探索者、落地建设者、监管者四个后台子代理。做出的番茄钟通过了它自带的计时测试，落地后的提示音参数和 demo 逐项一致。两步没照做：派工时没开监管者，没出第一份阶段报告 |
| 第二轮 | 同上。之前在适配文件里补了“派工这一步的顺序”和传话的格式 | 走通，约 10 分钟。监管者在派工时开了；传话用“用户说：”和“调度者：”分开；监管者第 2 次巡检靠读文件，查出总建设者的回报和实际不符。第一份阶段报告还是来不及出 |
| 第三轮（短） | 立项、派工、探索者第一次请用户听 demo。之前把“派工后出阶段报告”改成了“派工后先说一句话” | 照着做了。发现探索者起了一个本地服务没有停，适配文件加了一条规矩 |

每一轮的产出都复查过：开工确认、派工单、阶段报告都过了检查脚本；调度者和它开出的子代理，都没有读写项目目录和技能目录以外的文件。

**没有验证的：**

- 子会话这种开法由一个没有上下文的调度者来走。上面那一次，调度者是照着适配文件手动走的，带着上下文。
- 用 `/demo-first` 斜杠命令加载技能这一步。实跑时是直接把技能目录告诉调度者的。
- 终端里的命令行版。实跑是在桌面应用里做的。
- 调度者是主会话时的表现。实跑里调度者自己是一个子代理，由它再开子代理。开任务、交回、续上的机制一样，但主会话“说完话就等通知”的节奏没有测到。
- 真人用户。用户的话是照剧本给的，没有人真的听过提示音。
- Sonnet 5.5 以外的模型。
- 两个以上探索者同时等用户时的传话；按天算的长项目；交付这一步。

## 自己试一次

大约 15 分钟。

1. 装上技能，然后新开一个会话：

```bash
git clone https://github.com/wowsunny/demo-first ~/.claude/skills/demo-first
```

2. 在一个空目录里启动 Claude Code，发下面这段话：

```text
/demo-first
我想做：一个网页版的番茄钟。25 分钟倒计时，结束时有提示音，并显示一句鼓励的话。
什么时候交：从现在起 2 小时，北京时间（+08:00）
交什么：能在本机浏览器里直接打开的页面和代码
没把握的地方：结束时的提示音用哪一种好听又不吓人
```

3. 边看边记。做到探索者的提示音定稿、你说一次“报告”为止。

在桌面应用里，它应该把探索者和总建设者开成子会话，侧栏里会多出几个会话；在终端里，应该开成后台子代理。监管者在两边都是子代理。

| 编号 | 看什么 | 结果 | 备注 |
|---|---|---|---|
| C1 | 输入 `/demo-first` 后技能有没有加载；它有没有先读 `references/claude-code-platform.md` | | |
| C2 | 它运行 `init_ledger.py` 时，脚本的路径对不对；有没有因为找不到 `python3` 卡住 | | 技能目录的路径是： |
| C3 | 开工确认的最后一段，是不是照它要用的开法写的（“各开一个会话”或“后台子代理”）；发完有没有停下来等你 | | |
| C4 | 你回“开”之后：是不是先生成并检查派工单，再开任务，接着开监管者 | | 开了几个，哪一种： |
| C5 | 任务要运行命令或写文件时，批准的提示出现在哪：子会话的在它自己那里，子代理的在主会话里 | | |
| C6 | 桌面应用：它有没有告诉你先去哪个探索者的会话、给了能点的链接，你进去能不能直接聊。终端：探索者拿出 demo 后，它有没有马上叫你来看，并说“直接在这里回我” | | |
| C7 | 桌面应用：探索者每轮结束，有没有把【回报】写进 `coord/tasks/<编号>.md`，主会话有没有去读。终端：你回话之后，它是不是把你的原话转给探索者，而不是自己动手改 demo | | |
| C8 | 它有没有自己下场写正式项目的代码 | | |
| C9 | 你说“报告”：阶段报告是不是 20 行以内、“要你做的”不超过 3 件；监管者是不是新开的子代理 | | |

哪一步它没照做，把它当时的原话记下来。这比“成 / 不成”有用：看得出是适配文件没写清楚，还是平台的行为和文档写的不一样。
