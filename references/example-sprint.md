# 样例：四小时做一个“说完就有待办”的网页工具

一次冲刺从头到尾的样子。项目、链接和技术结论都是虚构的，只用来示范每一种文字该写成什么样；不要把里面的技术结论当事实。

## 0. 用户的话

> /demo-first 做一个网页工具：对着手机说一段话，它自动整理成待办清单。今天 18:30 前（北京时间）要交线上链接和代码，计时从 14:30 开始。

三样都齐了：做什么、什么时候交、交什么。不用再问。

## 1. 立项

```bash
python3 $SKILL/scripts/init_ledger.py --goal "说一段话，自动整理成待办清单的网页工具" --deadline 18:30 --start 14:30 --tz +08:00
```

脚本算出的关口：立项截止 14:42，探索截止 16:30，功能冻结 17:18，开始交付 18:06。并行上限：2 个探索者、2 个建设者、1 个监管者。单个探索最长 36 分钟。

**验收项**（写进 `coord/CHARTER.md`）。每条都是“用户做什么 → 看到什么”：

1. 按住按钮说“明天下午三点交周报，顺便订周五的会议室” → 松手后 5 秒内，清单里多出两条待办，其中一条带“明天 15:00”
2. 点一条待办的文字 → 能改内容和时间，改完立刻保存
3. 勾掉一条待办 → 它移到“已完成”，刷新页面还在
4. 点“分享” → 得到一个只读链接，别人打开看得到清单、改不了
5. 在手机上打开首页 → 不用横向滚动，说话按钮单手够得着

不好的写法：“语音识别准确”“界面美观”。没法当场验证，监管者也没法逐条对。

**拆任务树。** 对每一块问：做出来是什么样，现在说得准吗？

| 这一块 | 说得准吗 | 归谁 |
|---|---|---|
| 清单的增改查、勾掉完成、刷新还在 | 说得准，常规功能 | 总建设者 B1 |
| 只读分享链接 | 说得准 | 总建设者 B1 |
| 手机浏览器里把中文语音转成文字，3 秒内出字 | 说不准：有几条技术路线，在手机上各自稳不稳、快不快，要试了才知道 | 探索者 E1（选型） |
| 从一段口语里拆出一条条待办和时间 | 说不准：一句话两件事、“下周三”这种说法，模型能对几成 | 探索者 E2（功能） |
| 首页长什么样 | 说不准，看品味 | 探索者 E3（风格）。名额只有两个，先排队 |

E1 和 E2 直接决定验收项 1，所以先试它们；E3 排队，在它定稿之前总建设者先用默认样式。

**开工确认的后半段**（前半段是脚本填进去的初始设定）：

```
**二、任务树**

你回“开”之后，我在这个项目里给下面每一行各开一个独立任务：

- B1 总建设者｜边界、架构和骨架：清单的增改查、完成、存储、只读分享
- E1 探索者｜在手机浏览器里把中文语音转成文字，走哪条路能做到松手后 3 秒内出字
- E2 探索者｜从一段口语里抽出待办（事项和时间），10 句样例能对几句
- S1 监管者｜全局巡检
- 排队：E3 探索者｜首页视觉出 3 版给用户挑｜等 E1 或 E2 结束、探索者有名额再开

**三、要你定的**（不回就按推荐走）

1. 清单存在哪？推荐：存在服务器的数据库里，分享链接才做得出来。
2. 语音识别可以调用收费的模型接口吗？推荐：可以。E1 先试免费的办法，不够好再用收费的。
```

用户回：“开。两个都按推荐。”调度者把这两件定下的事加到 `coord/CHARTER.md` 末尾的“已经定了的事”一节，初始设定从此冻结。

## 2. 派工

```bash
python3 $SKILL/scripts/new_brief.py lead-builder B1 "边界、架构和骨架"
python3 $SKILL/scripts/new_brief.py explorer E1 "语音转文字走哪条路"
```

脚本填好了项目、时间、时间盒（E1 到 15:20）和各条规矩。调度者只填这几处。E1 的：

- **你要回答的问题：** 在手机浏览器里按住按钮说一句中文，松手后 3 秒内能不能拿到基本准确的文字（并说明走的是哪条路）？
- **你需要知道的事实：**
  - 验收项 1（原文）：按住按钮说“明天下午三点交周报，顺便订周五的会议室” → 松手后 5 秒内，清单里多出两条待办，其中一条带“明天 15:00”。这 5 秒里，后面“把文字整理成待办”那一步还要占大约 2 秒，所以留给语音转文字的只有 3 秒。
  - 用户已定：可以调用收费的模型接口，但先试免费的办法，不够好再用收费的。
  - 你只管“语音 → 文字”。“文字 → 待办”由另一个探索者 E2 在试，不用你做。
- **怎么算完成：** 用户在自己的手机上打开你的 demo，按住说验收项 1 里那句话，松手后 3 秒内页面上出现文字，“明天下午三点”“周报”“周五”“会议室”这四处都没有错。页面上同时显示这次用了多少秒。

注意三点：问题只有一个；事实是原文抄进去的，还替它算好了“5 秒里它占 3 秒”；完成的标准是用户能当场验证的现象。

想把 E3 也一起开，脚本会拦住：

```
错误：现在不该开这个任务，派工单没有生成。
  探索者到了并行上限（2 个）：E1、E2 还没结束。把这一个记进 BOARD.md 的“排队”，等前面的有了结论、运行过 clock.py --done <编号>，再来生成。
```

四个任务开完，调度者给用户发一条短消息，告诉他先去哪。这里不出阶段报告：

```
任务都开出来了：
- B1 边界、架构和骨架｜总建设者｜https://manus.im/app/…B1
- E1 语音转文字走哪条路｜探索者｜https://manus.im/app/…E1
- E2 从口语里抽出待办｜探索者｜https://manus.im/app/…E2
- S1 全局巡检｜监管者｜https://manus.im/app/…S1

先去 E1：它给出第一版 demo 后，用你的手机试着说一句。B1 会发来边界和架构的提案，有意见在那里回。
E3（首页视觉）先排队：探索者同时最多两个，语音和拆待办更影响验收项。
随时回来说“报告”，我查一轮。
```

## 3. 巡检

15:08，用户回来说“E1 好了，报告”。调度者运行 `clock.py` 看时间，然后去读各任务的最后一条消息。E1 的是：

```
【回报 E1】状态：完成
结论：成
做了什么：试了两条路。A 用浏览器自带的识别，B 录音后发给语音模型。A 在一部分手机上按住说话拿不到结果；B 在试过的两部手机上都稳，松手后 1.5～2.5 秒出字。
证据：demo https://…/e1-demo（页面上显示每次用时）。用户在自己的手机上试了 5 次，都在 3 秒内，四处关键词全对。
自己定的事：录音最长 60 秒，超过自动停 — 一段待办说不了这么久 — 错了的代价是长段话被截断
要谁决定：无
延后的事：没有网络时的提示；用户不给麦克风权限时的提示
下一步：无，等落地

移交说明 E1
1. 结论：成。走“录音后发给语音模型”这条路。
2. demo：https://…/e1-demo。打开，按住中间的按钮说话，松手，看下方的文字和用时。
3. 落地时必须保持的：按住才录、松手即发；松手后立刻显示“正在识别”；用户原话：“松手以后要马上有反应，哪怕先给个转圈。”
4. 建议的接口：transcribe(录音) → { 文字, 用时毫秒 }；失败时返回错误原因。
5. 踩过的坑：路线 A 不要再试；两种手机浏览器各自支持的录音格式不一样，demo 里的 pickFormat() 已经处理。
6. 没解决的和延后的：没有网络、没有麦克风权限时的提示。
7. 验收对照：① 松手后 3 秒内出字 ② 验收项 1 那句话四处关键词都对 ③ 松手后立刻有“正在识别”的反馈。
8. 相关文件：demo/index.html、demo/recorder.js（约 80 行，太长不贴，落地时从这个任务里取）。
```

调度者照处理表做：把移交说明存成 `coord/handoffs/E1.md`；运行 `clock.py --done E1`；探索者有名额了，开排队的 E3；B1 的回报说骨架里已经有 `transcribe()` 的假实现，于是进第 4 步。然后运行 `clock.py --card` 生成草稿 `coord/reports/1.md`，填好，查过，发出：

```
【阶段报告 #1｜已用 0:40，剩 3:20｜阶段：试与建】
一句话：语音转文字试成了，开始写进正式项目；拆待办还在试。

- E2 从口语里抽出待办｜探索者｜进行中｜10 句对了 7 句，在调“下周三”这类说法｜https://manus.im/app/…E2
- B1 骨架｜总建设者｜等用户｜骨架能打开；有一张“添加密钥”的卡片等你点｜https://manus.im/app/…B1
- B2 把语音输入写进正式项目｜落地建设者｜进行中｜刚开｜https://manus.im/app/…B2
- E3 首页视觉出三版｜探索者｜进行中｜刚开｜https://manus.im/app/…E3

要你做的（最多 3 件，最急的在前）
1. 去 B1：点“添加密钥”的卡片。有卡片等你点
2. 去 E3：它会给出三版首页，挑一版。要你定

我替你定了的（可以推翻）
- 语音输入交给新开的 B2 落地，不占 B1 的手 — 它的区域（录音和识别）和别处分得开

监管者的提醒
- B1 的骨架里分享链接谁都能改清单，和验收项 4“改不了”不符。建议去 B1 说

接下来
- E2 的时间盒到 15:22，到点我要它给结论。B2、E3 在跑。
```

这份报告正好 20 行（不算空行）。“要你做的”只有两件，都写了去哪个任务、做什么。E2 的进展是知会，没有占用户的名额。

监管者那条提醒本该转给 B1，但 B1 正在等用户点卡片，这时给它发普通消息会让它跳过那个动作。所以调度者把要说的话记进 `coord/BOARD.md` 的“待发的消息”，等用户点完再发。

## 4. 落地

```bash
python3 $SKILL/scripts/new_brief.py landing-builder B2 "把语音输入写进正式项目" --handoff E1
```

脚本已经把 `coord/handoffs/E1.md` 的全文填进了“移交说明”一节，一字不改。调度者填的几处：

- **你要落地的东西：** 把“按住说话 → 文字”写进正式项目，换掉 `transcribe()` 现在的假实现。
- **接入位和约定：** 从 B1 回报的“接入位”一栏原文抄来：接口 `transcribe(录音) → { 文字, 用时毫秒 }`；假实现在 `src/voice/transcribe.ts`。其余的约定请它读代码库里的 `coord/ARCHITECTURE.md`。
- **范围：** 只许动 `src/voice/` 目录。
- **怎么算完成：** ① 在正式项目的首页按住说话，松手后 3 秒内，文字交到下一步 ② 说验收项 1 那句话，四处关键词都对 ③ 松手后立刻出现“正在识别” ④ `src/voice/` 以外没有改动。

开任务时附上正式项目的网站，并把 E1 的任务作为任务引用附上。

B2 回报“完成”后，调度者照“怎么算完成”逐条比过，运行 `clock.py --done B2`，发消息请 B1 同步并发布；B1 回报同步完了，再请 S1 看这一块。

## 5. 交付

17:18 过了功能冻结。S1 的延后清单有四条，调度者交给用户挑，用户挑了“没有麦克风权限时的提示”，其余三条写进已知问题。18:06 开始交付，调度者自己在线上链接上把五条验收项走了一遍，然后写：

```
【交付说明】说完就有待办
- 线上链接：https://…
- 代码：正式项目“voice-todo”，已同步到 GitHub：https://…
- 验收项：1 通（实测 4.1 秒） 2 通 3 通 4 通 5 通
- 各任务：B1 https://… ｜B2 https://… ｜E1 https://… ｜E2 https://… ｜E3 https://… ｜S1 https://…
- 探索的结论：E1 成，录音后发给语音模型；E2 降级，只认“今天、明天、星期几、几点”，“下周三”这类按下一个周三算；E3 成，用户挑了第二版
```
