# 做得久的项目

项目要做好几天时，流程还是 SKILL.md 的四步，下面几处要留意。

## 要留意的地方

| 事项 | 怎么办 |
|---|---|
| 会话多了 | 同时开着的探索者不超过 3 个，这个上限和项目多长没有关系：每多一个会话，用户就多一处要去的地方。其余的留在“待探索”，有名额了再开 |
| 探索拖得久 | 派工单里的规矩是：同一个方向来回三轮定不下来，就停下来给判断。一个探索聊了一两天还没收敛，多半是问题太大：回调度者那里，把它砍小，或者拆成先后两个问题 |
| 监管者 | 对话变长后会带上成见。每做完一大段换一个新的：回调度者那里，`clock.py --done S1`，再 `new_brief.py supervisor S2`；把上一任的 `coord/WATCH.md` 全文贴给新的监管者 |
| 巡检怎么触发 | 用户去监管者那里说“巡检”。不想反复去说，就建一个定时自动化，见 `manus-platform.md` 第四节 |
| 建设者 | 它的对话也会变长、被压缩。`coord/ARCHITECTURE.md` 和它的任务文件是它的记忆：隔天接着做，先重读。对话长到反应变慢时，请用户新开一个任务接手，把同一份派工单贴进去：新任务只要读代码库里的 `coord/` 就能接着做 |
| 调度者 | 派完工就退出主线。隔天被叫回来时，先读 `coord/BOARD.md` 和 `coord/DECISIONS.md`，不凭印象 |

## 中途改初始设定

项目长了，用户难免要改目标。改动只能由用户提出或点头，回调度者那里做：

1. 改 `coord/CHARTER.md`，在 `coord/DECISIONS.md` 记一条：改了什么、为什么、哪些会话受影响。
2. 把改动的原文发给所有会话，请每个会话先回一句它理解的改动；并更新项目主指令。监管者的基准跟着换。
3. 已经落地的部分，请监管者对照新设定查一遍。
4. 用户定过期限、现在要改：`init_ledger.py --retime --deadline "<新的时间>"`。期限只显示在全景页上给用户看。
