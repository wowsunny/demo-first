# 按天算的项目

总时长超过一天时，`init_ledger.py` 会标成“项目档”。流程还是 SKILL.md 的五步，下面几处不同。

## 不同的地方

| 事项 | 冲刺档（不到一天） | 项目档 |
|---|---|---|
| 并行上限 | 2 个探索者、2 个建设者、1 个监管者，任务树 2 层 | 不设上限。但每多一个任务，用户就多一处要看的地方：同时让用户深度参与的任务不超过 3 个 |
| 阶段报告 | 用户说“报告”时出 | 每天至少出一份，哪怕没人问；每个探索定稿、每块落地之后各出一份 |
| 监管者 | 一个，用到交付 | 对话变长后会带上成见。每过一个关口换一个新的：`clock.py --done S1`，再 `new_brief.py supervisor S2 "全局巡检"`，把上一任的 `coord/WATCH.md` 全文抄进新派工单的“现在有哪些任务”后面 |
| 探索的时间盒 | 最长是总时长的 15% | 同样的比例，但换算出来可能是十几个小时。超过半天的探索先拆成两个问题 |
| 巡检怎么触发 | 用户催 | 建一个定时自动化，见 `manus-platform.md` 第四节 |
| 调度者自己 | 一个任务用到底 | 你的对话也会变长、被压缩。台账是你的记忆：每天开工先读 `coord/BOARD.md` 和 `coord/DECISIONS.md`，不凭印象。对话长到反应变慢时，请用户新开一个任务接手：新任务只要读 `coord/` 就能接着做，这正是台账的用处 |

## 多层的任务树

项目档可以分层：一个探索方向下面再拆子方向（E1.1、E1.2），一个大区域下面再分落地建设者。

- 仍然由你来开所有任务，层级只体现在编号和 `coord/BOARD.md` 里。子任务自己开子任务的做法，平台文档没有写明，见 `manus-platform.md` 第一节。
- 上级任务负责汇总下级：给上级发消息时，附上下级的回报原文。
- 每层只在自己这一层做决定。下级发现上级的方向有问题，写进回报，不要自己改道。

## 中途改初始设定

项目长了，用户难免要改目标。改动只能由用户提出或点头：

1. 改 `coord/CHARTER.md`，在 `coord/DECISIONS.md` 记一条：改了什么、为什么、哪些任务受影响。
2. 交付时间变了：`init_ledger.py --retime --deadline "<新的时间>"`，把新关口抄进 `CHARTER.md`。
3. 把改动的原文发给所有任务，并更新项目主指令。监管者的基准跟着换。
4. 受影响的探索重新定时间盒；已经落地的部分，请监管者对照新设定查一遍。
