## 一、动作和 SKILL.md 写的不一样

官方文档对下面这些行为没有写明。SKILL.md 按最可能的情况写；实际不是那样时，照右边做，并把你观察到的情况记一条到 `coord/DECISIONS.md`。

| 你遇到的情况 | 怎么办 |
|---|---|
| 开不出独立任务；或者开出来的任务一直排队不跑（账号同时只能跑一个任务） | 退成单任务，见本节末尾 |
| 用户回了“开”，平台仍然不让你开任务 | 平台只在用户明确要求时才开独立任务。请用户在当前任务里再说一句：“在此项目中，为分工表的每一行各开一个独立任务。” |
| 当前任务不在 Project 里，用户也不想建 | 照常做。新会话只带着派工单开始（派工单本来就自含），只是不会归在一起，也没有项目主指令。跳过“写进主指令”那一步 |
| 开任务时指定不了标题 | 派工单的第一行就是会话名，平台多半会照它起名。名字不对：在给用户的短消息里列出每个会话该叫什么，请用户在侧栏里手动改 |
| 开任务时指定不了档位；或者用户在模式菜单里看到的档位和你指定的不一样 | 在给用户的短消息里写明每个会话该是哪一档，请用户进各会话的模式菜单改 |
| 开任务时附不了任务引用 | 建设者：落地时它会请用户把移交说明贴过去、把 demo 文件传上去；用户嫌麻烦，可以回你这里说“转交 <编号>”，你去读那个探索者的最后一条消息，原文发给建设者。监管者：见下面“你留下当转交的人” |
| 监管者第一次巡检的第一行写着“读不到别的任务” | 见下面“你留下当转交的人” |
| 查不到某个任务的状态，或读不到它的消息 | 请用户打开那个任务，把最后一条【回报】贴给你 |
| 读得到任务的消息，读不到它工作区里的文件 | 回报和移交说明不受影响：派工单要求把它们全文放在最后一条消息里。demo 的文件，请用户从探索者那里下载、传给建设者 |
| 开不了子代理（没有工作流工具，或者申请调用次数被拒） | 小样改成记待探索；各会话手里的活按先后自己做。在给用户的短消息里说明 |
| 子代理在跑的时候，用户发来的消息你回不了 | 小样改成：先把这一轮聊完，再开子代理，并告诉用户大约等几分钟 |
| 子代理写的文件你读不到 | 让它把内容直接放进交回的文字里（单文件的 demo 贴全文），你来存成文件 |
| 预计要开的子代理超过 20 个 | 平台会先停下等用户确认，你替不了。能合并的任务书先合并 |
| 有任务没守“不发布” | 请用户在网站的项目设置里关掉 Agent Publish，之后每次发布都要用户确认 |
| 某个会话自己又开了独立任务 | 允许，但要它把链接写进回报。用户回你这里时，把它记进 `coord/BOARD.md`，并告诉监管者 |
| 用户在 Project 里手动开了一个任务 | 问清它的角色，用 `new_brief.py` 补一份派工单请用户贴进去，记进 `coord/BOARD.md` |
| 给任务发了消息，它没有动 | 查它的状态。在等用户确认：请用户去点，不要再发。已停：再发一条消息能让它重新跑起来 |
| 任务书太长，发不出去（一条消息约 5000 个估算 token） | 删掉“你需要知道的事实”里和这个会话无关的；还超，就把初始设定里验收项以外的部分压短 |

**你留下当转交的人。** 监管者读不到别的会话时：

1. 在交棒的短消息里告诉用户：这个账号上监管者读不到别的会话；想巡检时，先回你这里说“巡检”。
2. 用户说“巡检”：读每个会话最后一条消息里的【回报】，把原文（不改写）连同现在的钟点发给监管者，请它巡检。然后告诉用户去监管者那里看结果，不等它。
3. 你只转交，不替监管者下结论。

**退成单任务。** 四个角色变成当前任务里的四个阶段，台账照写：

1. 深聊照做。没把握的问题，在 `lab/<编号>/` 里各做一个最小 demo，用户看过后定稿，写移交说明到 `coord/handoffs/<编号>.md`。
2. 建设：另起正式项目，先写 `coord/ARCHITECTURE.md`，再照移交说明把 demo 重写进去。不直接把 `lab/` 里的代码搬过来。
3. 监管：每做完一段（定了分工、落地完、交付前），请用户在 Project 里手动新开一个任务，把 `new_brief.py supervisor` 生成的派工单贴进去，做一次冷启动检查。这一步不能省，自己检查自己查不出偏离。

## 二、思考强度和子代理

### 独立任务的档位

`new_brief.py` 每生成一份派工单，都会说这个会话该用哪一档。开任务时不指定，新任务会是哪一档没有定论（见第六节），所以每次都要写明。

| 脚本说的 | 开独立任务时 | 默认给谁 |
|---|---|---|
| 标准 | 标准模式（standard） | |
| 高 | Max 的高档（max-high） | |
| 超高 | Max 的超高档（max-extra） | 探索者、建设者 |
| 极致 | Max 的极致档（max-ultra） | 监管者；调度者由用户自己选，建议这一档 |

- 任务自己说不出自己是哪一档。以你开任务时指定的为准，写进给用户的短消息；用户可以在那个任务的模式菜单里核对、改。
- 档位越高，每一轮越慢。深聊是来回对话：用户嫌你慢，就建议他把你这个任务降到超高。

### 子代理

子代理是一个任务在内部用工作流工具开出来的，和独立任务不是一回事：

| | 独立任务（会话） | 子代理 |
|---|---|---|
| 在哪 | 和主任务并列，出现在任务列表里 | 在开它的任务内部，不出现在任务列表里 |
| 用户能不能进去聊 | 能 | 不能。做完只交回一次，中途发不出消息 |
| 结果 | 留在那个任务里 | 先回到工作流脚本，脚本返回什么，你就收到什么 |
| 档位 | 细到 Max 的几档 | 只有 lite、standard、max，**不设就是 lite**。本技能一律用 max |
| 文件 | 云端各有一台机器；本机模式下共用用户选的文件夹 | 默认和开它的任务共用环境，它写的文件开它的任务读得到 |
| 工具 | 全套 | 用不了建站工具、浏览器，也开不了任务：这几样只有开它的任务能用 |

怎么开（下面是工具说明里写的；标“没实测”的还没验证过）：

- **用一段脚本编排。** `agent(任务书, {effort_level: 'max', …})` 开一个子代理；`parallel(组名, …)` 让一组同时跑。脚本只做编排，里面不能读写文件、联网、取时间。
- **先申请调用次数。** 按实际要开的个数往高估。预计或上限超过 20 次，平台会先停下等用户确认。
- **交回的格式可以强制。** 给 `agent()` 指定输出格式（JSON Schema），交回不合格式会被打回。把 `templates/rules-subagent.md` 里的交回格式写成六个字段。
- **文件要明确交给它。** 要子代理读的文件列进它的 `input_files`，只在任务书里写路径不会传过去（没实测）。它写的文件不随结果带回：让它写到你指定的、互不冲突的固定路径，交回后你自己去读（没实测）。
- **失败不连坐。** 默认一个子代理失败不影响别的，成功的结果照样保留。后面的步骤离不开每一步时，才改成一个失败就全停。
- **汇总。** 脚本里可以把几个子代理的结果交给另一个子代理处理，只返回它的输出，这样你只收到汇总后的结果。它不是隔离：原文在任务状态里仍然查得到。
- **建站、预览、发布、在浏览器里验收，都得会话自己做。** 子代理用不了这几样工具，只能写代码文件、查资料、跑命令。
- **开了子代理不要干等。** 等子代理交回是一个单独的“等待”动作，给用户的话要写在它前面：开了子代理，就在同一条回复里接着问用户下一轮，或者说明现在在等什么。
- **所有会话的子代理共用一个并发上限**，数值看不到。几个会话同时开子代理，可能要排队。
- **工具说明的建议和本技能不一样。** 工具说明建议两三个小任务不用工作流、一般用 lite。本技能的做法是用户定的：能单独展示的两三块也并行，档位用 max。照派工单做。

## 三、各会话共用一个文件夹

默认每个任务各有一台云端机器，互相看不到文件，所以台账分散在各自的工作区里，靠派工单、回报、移交说明和任务引用来传。下面两种情况，各会话和你在同一个文件夹里工作，做法省事得多：

| 情况 | 依据 |
|---|---|
| 用户在桌面应用里打开了 Work locally，选了一个文件夹 | 官方文档写明：同一台设备、同一个文件夹里的任务看到的是同一批文件，平台不做副本。实测（2026-11-20，Windows）：主任务开出来的任务继承设备和文件夹，能读写同一个文件 |
| 账号开了 Cloud Computer（一台常开的云端机器） | 官方博客写明所有任务共用一块硬盘。哪个任务用它由平台逐个决定 |

**开第一个会话时顺带验证。** 桌面应用里实测是共用的，别的环境没测过。所以第一个会话就用下面第 1 条“只发路径”的开法：它读得到派工单，说明是共用的，后面都照这一节做；它回“读不到派工单”，就把派工单全文发给它，后面全照 SKILL.md 的默认做法，这一节不用再看。

共用时有五处不一样：

1. **派工单只发路径，不用把全文再打一遍。** 派工单照样生成、填、查。开任务时第一条消息只写这三行（第一行是会话名，平台多半照它给任务起名）：
   ```
   # <会话名>
   你的派工单在工作区的 coord/briefs/<编号>.md。现在把它完整读一遍，照它做。
   读不到这个文件，就只回一句“读不到派工单”，然后停下。
   ```
   标题和思考强度照脚本说的指定。任务引用可以不附：文件它都读得到。
2. **全景页可用。** 在交棒的短消息里，请用户用浏览器打开 `coord/progress.html`（给完整路径）。它每 10 秒自动刷新：分工和进展是一棵树，等用户处理的事顶在最上面，监管者没处理的清单单列一栏。各会话的派工单里已经写了怎么记进展。
3. **建设者落地时直接读文件。** 移交说明在 `coord/handoffs/<编号>.md`，demo 在 `lab/<编号>/`。派工单里已经写了。
4. **监管者直接读文件。** 它不靠任务引用，所以第一次巡检不会说读不到，你可以直接交棒。
5. **每个文件仍然只有一个写者。** 平台没有说两个任务同时写一个文件会怎样。探索者只动 `lab/<编号>/` 和它自己在 `coord/` 下的那几个文件；正式项目的目录只归建设者。

在用户自己的电脑上干活，另外要知道：

- **Windows 上的终端是 PowerShell，没有 `python3` 这个命令**，用 `python`。脚本生成的派工单和提示，已经照你运行脚本时用的那个名字写了。
- **预览地址只有这台电脑打得开。** 要在手机或别的设备上看，得先发布。
- **正式项目要建成 Manus 托管的网站项目**，才有数据库、登录和线上链接；普通的本地文件夹没有发布这一步。发布时会问 Allow Manus to publish?，第一次请用户点 Allow once，之后可以选 Always allow for this website。
- **本机项目还不能回滚。** 动大改之前，请建设者先存一个版本；要更稳，请用户让 Manus 在这个文件夹里建一个 Git 仓库。
- **Windows 上两种审批模式要先点一次 Enable safe modes。** 默认的 Approve for me 只拦修改，不拦读取。
- 某个功能本机做不了时，任务会临时切到云端（显示 Switched to Cloud · Temporary）。这时它要是说读不到文件，等它切回来再让它接着做。

别的共用办法，没有上面这么省事，规矩一样（先让一个会话验证读得到，每个文件只有一个写者）。它们靠连接器，而工具说明里写着本机模式下外部连接器不可用，所以只在云端的任务里用得上：

- 正式项目的代码同步到了 GitHub：连了 GitHub 的任务都能读写这个仓库，把整套台账放进仓库的 `coord/`。
- 各会话连了同一个网盘类的连接器（比如 Google Drive）：在网盘里建一个 `coord/` 文件夹，当作共用台账。

## 四、让巡检自动进行

任务不会自己醒来。默认靠用户去监管者的会话里说“巡检”。用户不想反复去催时：

1. 请用户在监管者的任务里说一句：“建一个定时自动化，每 15 分钟在这个任务里巡检一次（平台最短 5 分钟）；没有要提醒的，就只回一句‘无变化’。”
2. 自动化启用前，平台会请用户审核。
3. 交付后提醒用户删掉它：Automations → Manage → More actions → Delete。

每多一个定时任务就多一份积分消耗，监管者用的又是最高档。用户没提，就不要开。

## 五、正式项目是游戏或移动 App

正式项目只有建设者一个会话在改，所以不需要几个任务同时改同一个项目：游戏类项目、移动 App 都照常做。探索者的 demo 照常放在各自的工作区里，做成单页或很小的工程。

## 六、平台事实和出处

| 事实 | 出处 |
|---|---|
| 提出要求的那个任务是主任务，它能查进度、读各任务的结果、给一个或全部任务发消息 | 并行任务 |
| 平台只在用户要求时才开独立任务。主任务第一次需要这个权限时弹出 Allow these actions?，用户点 Allow in this task | 并行任务 |
| 新任务只带着派工单和项目上下文（主指令、文件、技能、连接器、网站）开始，看不到主任务的对话 | 并行任务 |
| 任务之间读不到彼此的对话，只有主任务能替它们去读 | 并行任务 |
| 同一台电脑上的任务可以共用文件；同一台设备、同一个文件夹里的任务看到的是同一批文件，平台不自动做副本 | 并行任务 |
| 项目主指令的更新，各任务从下一条消息起生效；项目文件的更新，只对之后新开的任务生效 | 项目 |
| 动作确认只能在各自的任务里做。任务等确认时，收到普通消息会跳过那个动作 | 并行任务、任务生命周期 |
| “已停”不一定是终态，新消息、定时或后台工作都能让任务再跑起来 | 任务生命周期 |
| 几个任务改同一个网站：共用一份版本历史、一个数据库、一个已发布站点。任何任务一发布，整站就上线 | 在新任务中编辑 |
| 云端网站默认由 agent 直接发布，不问用户；在网站设置里关掉 Agent Publish 后，每次发布都要确认 | 网站相关的卡片 |
| 任务引用：给任务附上最多 20 个其他任务，它可以按需去读它们的提纲、对话和文件 | 任务引用 |
| 主任务用工具开任务时能附任务引用。被附的任务读得到对话，读不到文件（列文件时返回“没有文件”） | 2026-11-20 实测（Windows 桌面应用，Work locally） |
| 主任务开出来的任务继承设备和文件夹，能读写同一个文件 | 2026-11-20 实测（Windows 桌面应用，Work locally） |
| 开任务的工具有标题参数，可以直接指定会话名（侧栏里的显示没有亲眼核对） | 2026-11-20 实测（Windows 桌面应用，Work locally） |
| 一条消息的文字约限 5000 个估算 token；开任务、发消息各限每分钟 10 次 | 建任务、频率上限 |
| 定时自动化最短间隔 5 分钟，可以在同一个任务里续跑，启用前要用户审核 | 自动化 |
| 主任务开独立任务时可以指定档位，指定了就照指定的来。任务自己说不出自己是哪一档 | 2026-11-20 实测 |
| 不指定档位时新任务是哪一档，没有定论：一次实测里是 max-extra，分不清是跟着主任务，还是平台的默认值 | 2026-11-20 实测 |
| 任务内部可以用工作流工具开子代理：不出现在任务列表里，不和用户对话，结果以文字交回；档位只有 lite、standard、max，不设就是 lite；开之前要申请调用次数 | 2026-11-20 实测 |
| 子代理写的文件，开它的任务读得到 | 2026-11-20 实测（Windows 桌面应用，Work locally） |
| 子代理运行时，用户发来的消息进得来、主任务也能回。只测过一个 20 秒的子代理，跑得久时怎样没测 | 2026-11-20 实测（Windows 桌面应用，Work locally） |
| 工作流脚本的其余细节（输出格式、`input_files`、失败策略、20 次以上要确认、汇总的写法） | 2026-11-20 Manus 照工具说明自述，没实测 |
| 子代理用不了建站工具、浏览器，也开不了任务；等子代理是一个单独的“等待”动作；所有会话的子代理共用一个并发上限；本机模式下外部连接器不可用 | 2026-11-20 工具说明，没实测 |
| 桌面应用在 Windows 上的终端是 PowerShell，没有 `python3` | 2026-11-20 实测（Windows 桌面应用，Work locally） |
| 积分的一个参考：四条很小的机制测试共用了 455 积分，每个顶层任务起步 85～105 | 2026-11-20 实测 |
| Cloud Computer：一台常开的云端机器，文件和装的工具在任务之间保留，所有任务共用一块硬盘 | Cloud Computer |
| 桌面应用里打开 Work locally，任务就在用户电脑上选定的文件夹里干活；Windows 上两种审批模式要先点一次 Enable safe modes；本机做不了的功能会临时切到云端 | 桌面应用 |
| 在本机建站：预览只有这台电脑打得开；Manus 托管的项目才有数据库、登录和发布；发布时问 Allow Manus to publish?；只有项目所有者能发布；本机项目还不能回滚 | 在本机建站 |
| 分叉（Branch）：从某条回复开出一个新任务，带上到那一条为止的对话、文件和指令 | 分叉 |
