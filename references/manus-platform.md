## 一、动作和 SKILL.md 写的不一样

官方文档对下面这些行为没有写明。SKILL.md 按最可能的情况写；实际不是那样时，照右边做，并把你观察到的情况记一条到 `coord/DECISIONS.md`。

| 你遇到的情况 | 怎么办 |
|---|---|
| 开不出独立任务；或者开出来的任务一直排队不跑（账号同时只能跑一个任务） | 退成单任务，见本节末尾 |
| 用户回了“开”，平台仍然不让你开任务 | 平台只在用户明确要求时才开独立任务。请用户在当前任务里再说一句：“在此项目中，为任务树的每一行各开一个独立任务。” |
| 当前任务不在 Project 里，用户也不想建 | 照常做。新任务只带着派工单开始（派工单本来就自含），只是不会归在一起，也没有项目主指令。跳过“写进主指令”那一步 |
| 查不到某个任务的状态，或读不到它的消息 | 请用户打开那个任务，把最后一条【回报】贴给你。在 `coord/BOARD.md` 里注明：这个任务靠用户转述 |
| 读得到任务的消息，读不到它工作区里的文件 | 不影响：派工单已经要求把回报和移交说明全文放在最后一条消息里。哪个任务没照做，发消息请它贴出来 |
| 开任务时附不了任务引用 | 监管者：把它派工单里“你怎么看到它们”一节换成第二种说法，每次请它巡检时贴上各任务最新回报的原文，不改写。落地建设者：请探索者把关键代码贴进移交说明第 8 节，你抄进落地派工单 |
| 开任务时附不了网站，落地建设者改不到正式项目 | 请用户在正式项目的网站卡片上点 **Edit in new task**，把落地派工单全文贴进去发出。或者不开落地任务，把移交说明发给总建设者 |
| 别的建设者读不到代码库里的 `coord/ARCHITECTURE.md` | 改成由你中转：请总建设者把它的全文放进回报，你抄进每份落地派工单的“接入位和约定”一节 |
| 有任务没守“不发布” | 请用户在网站的项目设置里关掉 Agent Publish，之后每次发布都要用户确认 |
| 某个任务自己又开了子任务 | 允许，但要它把新任务的编号（接在自己的编号后面）和链接写进回报。你记进 `coord/BOARD.md`，下次请监管者巡检时告诉它 |
| 用户在 Project 里手动开了一个任务 | 问清它的角色，用 `new_brief.py` 补一份派工单请用户贴进去，记进 `coord/BOARD.md` |
| 给任务发了消息，它没有动 | 查它的状态。在等用户确认：请用户去点，不要再发。已停：再发一条消息能让它重新跑起来 |
| 开出来的任务档位不合适：太慢太费积分，或者太轻、做不好 | 请用户进那个任务，在模式菜单里换一档，并在阶段报告里写明换哪个任务、换成哪一档。探索者用标准档就够；监管者值得用高一档，它的用处就是找出别的任务没想到的问题 |
| 任务书太长，发不出去（一条消息约 5000 个估算 token） | 删掉“你需要知道的事实”里和这个任务无关的；还超，就把移交说明换成“在 <探索者编号> 任务的最后一条消息里，已作为任务引用附上” |

**退成单任务。** 四个角色变成当前任务里的四个阶段，台账照写：

1. 探索：每个没把握的问题在 `lab/<编号>/` 里做一个最小 demo，用户看过后定稿，写移交说明到 `coord/handoffs/<编号>.md`。
2. 建设：另起正式项目，先写 `coord/ARCHITECTURE.md`，再照移交说明把 demo 重写进去。不直接把 `lab/` 里的代码搬过来。
3. 监管：每到一个关口，请用户在 Project 里手动新开一个任务，把 `new_brief.py supervisor` 生成的派工单贴进去，做一次冷启动检查。这一步不能省，自己检查自己查不出偏离。

## 二、正式项目是游戏或移动 App

- **游戏。** Manus 有专门的游戏类项目，网页小游戏也可以用普通的网站项目来做。文档只写了网站和 App 可以几个任务同时改，没写游戏类项目。所以用户要做游戏时，在开工确认里加一个问题：建成普通网站项目行不行（推荐：行，这样几个任务才能同时改代码）。用户同意：之后照网站处理。用户要用游戏类项目：改代码就只留总建设者一个任务；探索者照常各做各的 demo；落地都交给总建设者，不开落地建设者；其余并行的任务只做素材、试玩、写说明。
- **移动 App。** 用户在网站卡片上点 **Edit in new task** 可以开第二个任务。由你开任务时，接口文档只写了能附普通网站。附不上就请用户手动开，把落地派工单全文贴进去。

## 三、各任务能共用一个文件夹或仓库

默认每个任务各有一台云端机器，所以台账分散在各自的工作区里，由你读回报来汇总。下面三种情况可以共用一份：

| 情况 | 做法 |
|---|---|
| 所有任务都是 Manus Studio 的本地任务，在同一台电脑、同一个文件夹里 | 整套台账放在这个文件夹的 `coord/` 里，各任务直接读写自己的文件。探索者的 demo 放 `lab/<编号>/`，正式项目放它自己的目录。由主任务开出来的任务是不是也在本地，文档没写：开出第一个任务后，先请它读一下 `coord/CHARTER.md`，读得到才这么做 |
| 正式项目的代码同步到了 GitHub | 连了 GitHub 的任务都能读写这个仓库，包括探索者和监管者。把整套台账放进仓库的 `coord/` |
| 各任务连了同一个网盘类的连接器（比如 Google Drive） | 在网盘里建一个 `coord/` 文件夹，当作共用台账 |

不管哪一种，三条规矩不变：每个文件只有一个写者；派工单里写清共用位置的路径；回报仍然放在每个任务的最后一条消息里，你读它最可靠。

## 四、让巡检自动进行

任务不会自己醒来。默认靠用户说“报告”来触发一轮巡检。用户不想反复催时：

1. 在当前任务里建一个定时自动化：每 10～15 分钟一次（平台最短 5 分钟），在这个任务里续跑，内容是“照 demo-first 第 3 步巡检一轮。任务状态都没变，就只回一句‘无变化’。”
2. 自动化启用前，平台会请用户审核。
3. 交付后提醒用户删掉它：Automations → Manage → More actions → Delete。

监管者也可以这样自己醒来，但每多一个定时任务就多一份积分消耗。冲刺档不建议给监管者单独设。

## 五、平台事实和出处

| 事实 | 出处 |
|---|---|
| 提出要求的那个任务是主任务，它能查进度、读各任务的结果、给一个或全部任务发消息 | 并行任务 |
| 平台只在用户要求时才开独立任务。主任务第一次需要这个权限时弹出 Allow these actions?，用户点 Allow in this task | 并行任务 |
| 新任务只带着派工单和项目上下文（主指令、文件、技能、连接器、网站）开始，看不到主任务的对话 | 并行任务 |
| 任务之间读不到彼此的对话，只有主任务能替它们去读 | 并行任务 |
| 项目主指令的更新，各任务从下一条消息起生效；项目文件的更新，只对之后新开的任务生效 | 项目 |
| 动作确认只能在各自的任务里做。任务等确认时，收到普通消息会跳过那个动作 | 并行任务、任务生命周期 |
| “已停”不一定是终态，新消息、定时或后台工作都能让任务再跑起来 | 任务生命周期 |
| 几个任务改同一个网站：共用一份版本历史、一个数据库、一个已发布站点。代码自动合并；数据库没有冲突保护；任何任务一发布，整站就上线；一个任务只能编辑一个网站 | 在新任务中编辑 |
| 别的任务存了新版本后，预览要点 Sync 才更新；agent 每次编辑前会自己加载最新代码 | 在新任务中编辑 |
| 云端网站默认由 agent 直接发布，不问用户；在网站设置里关掉 Agent Publish 后，每次发布都要确认 | 网站相关的卡片 |
| 任务引用：给任务附上最多 20 个其他任务，它可以按需去读它们的提纲、对话和文件 | 任务引用 |
| 一条消息的文字约限 5000 个估算 token；开任务、发消息各限每分钟 10 次 | 建任务、频率上限 |
| 定时自动化最短间隔 5 分钟，可以在同一个任务里续跑，启用前要用户审核 | 自动化 |
| 任务的档位：接口开新任务时不填就是标准档，不继承开它的任务；之后可以改。网页端并行任务开出来的是什么档位，文档没写 | 建任务、发消息 |
| 同时能跑的任务数：免费账号 1 个，Pro 20 个 | 套餐 |
| 每个任务各自计积分；只在任务实际处理时消耗，停着不耗 | 并行任务、积分规则 |
| 技能分三级加载：名字和描述在任务启动时加载；正文在触发时才读；脚本和参考文件在正文提到时才读 | 技能 |
| 新建网站或 App 之前会弹一张蓝图确认卡片；添加密钥、预留域名也各有卡片。网站默认直接发布、不问，游戏和移动 App 默认会问 | 网站相关的卡片 |
| Wide Research：一个任务内部最多同时处理 20 个同类的子项，自动触发，适合 10 个以上的同类条目 | Wide Research |
